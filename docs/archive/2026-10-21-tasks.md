# Tasks

> **Status: built** (API: migration `0080`, `apps/api/app/tasks/`, `tests/test_tasks.py`; web: `/tasks`, the item editor's Tasks tab, the bell and search, `tests/e2e/tasks.spec.ts`; search: migration `0081`, `search/documents.py::_tasks`, `tests/test_search_tasks.py`). **Not built:** rule/system-created tasks. Comment threads on a task: migration `0082` (see §11). Departures from this draft are listed in §11.

**Plan V1 source:** §10 "Tasks and Change Triggers". **Decided by:** Q524 = 1 (a real `task` table with assignment, due date, status). **Related:** Q521 (notifications in-app only), Q523 (comments with mentions), Q472 (rule engine, not built), Q528 (§7–§8 templates deferred).

---

## 1. What this adds

A task is a piece of work given to a person: a title, an assignee, a due date and a status, optionally pointing at the record it is about. Today there is nowhere to say "Sam, chase the hinge supplier by Friday" except a comment, which has no assignee, due date or done state.

## 2. Scope: what Q524 and Plan V1 §10 ask for, and what this spec builds

§10 lists six creation paths. This spec builds two.

| Path (§10) | This spec |
| --- | --- |
| Manually | **Built** |
| From another person/team request | **Built** (a task assigned to someone else, see §5) |
| By configured rules/conditions | **Not built.** Needs the Q472 rule engine, which does not exist |
| By workflow, from changes, from system events | **Not built.** Same reason; the `source` column (§3) leaves room for them |
| Change-impact suggestions (second paragraph of §10) | **Not built** |
| Template follow-ups (Q259) | **Not built.** Q528 defers templates |

Nothing here may be described as "tasks done"; the rule-created half of Q524's reasoning is deferred, not satisfied.

## 3. Data model (migration `0080`)

```
task
  task_id        bigserial PK
  workspace_id   FK workspace, NOT NULL
  title          varchar(200) NOT NULL, CHECK length(btrim(title)) >= 1
  description    text, nullable, CHECK length <= 5000
  status         varchar(16) NOT NULL DEFAULT 'open'
                 CHECK IN ('open','in_progress','done','cancelled')
  assignee_id    FK app_user, nullable          -- unassigned allowed (see §9 Q-T3)
  created_by     FK app_user, NOT NULL
  due_date       date, nullable
  source         varchar(16) NOT NULL DEFAULT 'manual'
                 CHECK IN ('manual')            -- widened when rule/system paths arrive
  -- attachment target: see §9 Q-T1. Shape (Q-T1 = project, item or cutlist, or none):
  project_id / item_id / cutlist_id  nullable FKs
                 CHECK num_nonnulls(project_id, item_id, cutlist_id) <= 1
  completed_at, completed_by, cancelled_at, cancelled_by
  created_at, updated_at
```

- `project_id` is always derivable (a task on an item or cutlist is in that item's project), so scoping goes through `projects.workspace_id` or the task's own `workspace_id` (§7 workspace isolation).
- A task on a soft-deleted item answers like any record of a deleted item: hidden from lists, 404 on direct read. Every SQL string that reads `items` or `cutlist` takes `row_types.not_deleted` / `live_joinery_items` (`tests/test_items_deleted_filter.py` will fail otherwise). Related parts are not valid targets (they have no thread, take or QC).
- Soft state only: tasks are cancelled, never hard-deleted.

## 4. Permissions

A new module `tasks` is not proposed. Tasks are cross-cutting, so they reuse existing grants instead of adding a 13th module (§5 says a module needs a `MATRIX` entry and a migration of `group_module_grant` rows).

- See / create / edit / complete a task: the **`comment`** action on the module that owns the target (`tracking` for project and item, `list` for cutlist). This mirrors how comment threads are gated and keeps "a user with only project-scoped memberships" behaviour identical to comments (workspace-wide grants only).
- A task with no target (§9 Q-T1) has no module to gate on. **Decided 2026-10-21:** any authenticated user may create a task for themselves; assigning one to someone else needs `comment` on `tracking`.
- Assignee and creator may always change status of their own task. A manager or admin may edit or cancel any.
- Assignee and any FK taken from a request body (`assignee_id`, target ids) are validated against the caller's workspace (`workspace_scope.user_in_workspace`, `project_in_workspace`, an item helper). Another workspace's row answers as a missing one, and `test_workspace_isolation_probe.py` / `_body_probe.py` / `_query_probe.py` must cover it with no `KNOWN_LEAKS` entry.
- Assigning to a user who cannot read the target is refused (`409 ASSIGNEE_CANNOT_READ_TARGET`, Q-T3).

## 5. API

Literal paths before parameterised ones (§8).

```
GET    /tasks?assignee=me|<id>&status=&project_id=&item_id=&due_before=&limit=&offset=
POST   /tasks
GET    /tasks/{id}
PATCH  /tasks/{id}            -- title, description, assignee, due_date, target; expected_versions
POST   /tasks/{id}/status     -- {status}; 409 TASK_CLOSED when leaving done/cancelled is refused
GET    /items/{id}/tasks      -- convenience for the item editor tab
```

- Refusals are `409 {detail: {code}}` with stable codes: `TASK_CLOSED`, `TASK_TARGET_DELETED`, `INVALID_STATUS`.
- PATCH schema calls `schema_guards.no_null(...)` for `title`, `status`, `created_by`, `workspace_id` (NOT NULL columns). Field-level `expected_versions` as for items (§8).
- Dynamic `SET` lists use `sql_columns.require_columns` against a fixed allow-list (`tests/test_sql_set_columns.py`).
- Every mutation writes `audit_log`; a task on an item also writes `item_edit_log` in the same transaction (§5).
- Lock interaction (§9 of CLAUDE.md): tasks are **deliberately not locked**, like comments and QC records: a Hard or Controlled lock on an item does not stop someone being asked to do something about it. Record this in the lock table's "Deliberately not locked" line when built.

## 6. Notifications

This is the part with a real design cost. Today `notification` is keyed on `comment_id` (`notifications/queries.py` joins `comment c ON c.comment_id = n.comment_id` and hides rows whose comment is deleted), and its `kind` check is `('mention','reply')`.

A task notification ("Sam assigned you a task", "task due tomorrow") has no comment. Two options, see §9 Q-T2:

1. **Derived, like `orders_waiting` and `lock_requests_waiting`.** `GET /notifications` adds `tasks_open` (newest 20, assigned to the caller, status open/in_progress) and a count on a first page, no table, no read state. Matches an established pattern and needs no change to `notification`.
2. **Real rows.** Widen `kind`, make `comment_id` nullable, add `task_id`. More work, gives read/unread and "assigned to you" events, but touches the table every comment notification flows through.

Email stays out (Q521).

## 7. Web

- **My tasks** list. Placement is an IA question: the six primary tabs are fixed (§6), so it goes on the **secondary strip** or the bell, not a seventh tab. Proposed: bell section "Tasks" (option 1 above) plus a `/tasks` page on the secondary strip.
- **Item editor**: a Tasks tab listing the item's tasks with an add box. Locks do not disable it (§5).
- Create/complete/cancel use existing patterns: cancel through `useConfirm()`; names through `askText`/`askFields`; no `window.confirm`. Cancel uses the confirm dialog only, with no 10-second undo (decided 2026-10-21): reopening is allowed (§9 Q-T3), so a mistaken cancel is recoverable.
- Types in `lib/tasks-types.ts`; `due_date` is a string `YYYY-MM-DD`. No new state library (§6).
- Design tokens only; JetBrains Mono for numbers/dates.

## 8. Search, tests, seed

- **Search:** tasks are not in Q576's type list. Adding them means a trigger in the migration and a loader in `documents.py` (a test enforces both), and an update to Q579's list. Proposed: **not in v1**; record as a deferral. Never index secrets or money.
- **pytest:** new `tests/helpers_tasks.py` builder; tests for each route, status transitions, soft-deleted-item targets, null-write 422s, and the three isolation probes. Tests that fix a bug must be shown failing against unfixed code.
- **e2e:** one spec that creates its own project and item through the API (never ALF-001), adds a task, completes it, and puts back what it added.
- **Seed:** a couple of tasks, written through the same query functions the API uses so audit rows are real; idempotent; created in a block that already owns its item, cutlist, area and room (§4 seed rules).
- CI: ruff `F401,F841,F811` over new files.

## 9. Decisions (answered 2026-10-21; every recommendation taken)

**Q-T1 = (a). What can a task attach to?** Under-specified in Plan V1 ("tasks" with no target stated).
Options: (a) one of project, item or cutlist, or none (shape in §3); (b) project and item only; (c) free-standing only, linked by a URL in the description. **Chosen: (a).** Cutlist owns the production workflow (Q412), so "CNC this" tasks belong there; the CHECK keeps it to one target. Comment threads on Area/Room/Module are not mirrored; adding them later is a column each.

**Q-T2 = option 1 (derived). Notification mechanism.** Option 1 (derived) or option 2 (real rows), §6. **Chosen: 1.** it matches `orders_waiting` / `lock_requests_waiting`, needs no change to `notification`, and cannot go stale. The cost is no "you were assigned this at 10:02" history; revisit when email (Q521) arrives.

**Q-T3 = all three. Edge rules.** Three small calls: may a task be unassigned? May a done/cancelled task be reopened? May you assign a task to someone who cannot read its target? **Chosen:** unassigned allowed (shows in a team view only); reopen allowed by assignee, creator, manager, admin (no `TASK_CLOSED` for them, the audit log keeps the history, consistent with Q513's "history for accountability, not restoration"); assigning to a user without read access refused with `409 ASSIGNEE_CANNOT_READ_TARGET` rather than leaking the name of a record.

## 10. Not in this spec

Rule-created and system-created tasks; change-impact suggestions (Q472 and §11's change engine); recurring tasks; sub-tasks; task comments (threads on a task would be a new comment object type: wait for demand, CLAUDE.md lists "Task and Change comment threads" as open and this would close the Task half); email or push; templates.

## 11. As built (API), departures from the draft above

- **Error codes.** `TASK_TARGET_DELETED` and `INVALID_STATUS` were dropped: a missing, soft-deleted, related-part or other-workspace target answers `404 {detail: "not found"}` (like a missing one, so the isolation probes pass), and a bad status is a 422 from the schema. Codes in use: `TASK_CLOSED`, `ASSIGNEE_CANNOT_READ_TARGET`, `ASSIGNEE_NOT_FOUND` (404), `FIELD_CONFLICT`.
- **Closed tasks.** Editing fields of a `done`/`cancelled` task is `409 TASK_CLOSED`; changing status (reopening) is not, for the creator, assignee, manager and admin.
- **Who may edit.** Creator, assignee, manager or admin, and also `comment` on the target's module (and on the new target when moving a task). Status changes need only creator/assignee/manager/admin.
- **List filters that name a record** (`project_id`, `item_id`, `cutlist_id`, `/items/{id}/tasks`) answer 404 when that record does not exist for the caller, so the query probe can tell a foreign id from a missing one. `project_id` also matches tasks on that project's items and cutlists.
- **PATCH targets.** Sending any of `project_id` / `item_id` / `cutlist_id` replaces the target with the one that is not null (or none).
- **Seed.** Two tasks on TRT-014 and with no target, made through `create_task`; none on an item (an item task writes `item_edit_log`).
- **Bell (§6, option 1).** `GET /notifications` carries `tasks_open` (at most 20, soonest due first) and `tasks_open_count` for every role on the first unfiltered page; `GET /tasks?status=active` (open + in progress) backs it. The existing exact-shape assertions in `test_comments*.py` gained the two empty keys.
- **Web.** `/tasks` is on the secondary strip, gated on `tracking:read`. It lists My tasks, All to do, Done and Cancelled and can create a task with no target; a task on an item is created from the item editor's Tasks tab (`tracking:comment`). Status is a select; Cancelled asks first (confirm dialog, no undo toast, per the decision); Rename is a one-box prompt. Errors go to `useUndo().notify`.
- **Search (decided 2026-10-21: index all, filter per row; a hit shows title + target label and opens `/tasks?task=ID`).** Departs from §8 ("not in v1") and amends Q576's type list by one. Every task is indexed (migration `0081`: a row trigger on `task`, four fan-out triggers for the embedded labels, the outbox check widened). The document carries `visibility` (`tracking` | `list` | `private`) and `private_to`; `GET /search` builds a `TaskScope` from the caller and `build_filter` adds `(type = task AND (visibility = "tracking" [if tracking:read] OR visibility = "list" [if list:read] OR <private clause>))`, where the private clause is every private task for a manager or admin and `private_to = <user id>` for anyone else. `TYPE_MODULE["task"]` is `None`. Done and cancelled tasks are `archived` (hidden unless "include archived"); a soft-deleted item or cutlist removes its tasks from the index. Meilisearch had to be started to check the filter on the real engine (`test_search_index.py::test_task_rows_are_filtered_by_visibility_and_person[meili]` runs on both implementations).
- **Linked task on `/tasks`.** `?task=ID` fetches that task if the list does not hold it (a search hit may be someone else's, unassigned or done) and pins it above the list; if it is not visible the page says so.
- **Project and cutlist entry points.** The project page has a Tasks card (`ProjectTasksCard`, `tracking:comment` to add) listing the project's own tasks and those on its items and cutlists (`GET /tasks?project_id=`), and a task added there is on the project. The cutlist detail in the List tab has a fourth pane, Tasks (`list:comment` to add), listing `GET /tasks?cutlist_id=`; a task added there is on the cutlist. Both are `TaskPanel` scopes (`project`, `cutlist`); no API or migration change.
- **Comments on a task (option (a): the thread mirrors the task's own rules; migration `0082`).** `comment.task_id` is the seventh target (same shape as `0043`'s). Read: whoever can see the task (`tasks.queries.get_task`), a 404 otherwise, so a no-target task's thread is private to its creator, assignee, managers and admins. Post, in a thread on a project, item or cutlist task: `comment` on the module its target follows (`tracking` / `list`); **on a task with no target, seeing it is enough** (the task is "free to make for yourself", so it has no module to ask a grant of; this is this spec's reading of "mirror the task's own rules" and a viewer on their own task may comment). Edit and delete are the existing author / manager rules. Mentions go only to people who can see the task, and a task thread's notification is hidden from a recipient who can no longer see the task (a deleted item's, a private task's) and returns if access does; the link is `/tasks?task=ID`, which opens the task's thread. A task on an item also writes `item_edit_log` rows for its comments. `GET /tasks` rows carry `comment_count` and `can_comment`; the web shows a Comments toggle on each task row (`TaskPanel`, so on `/tasks`, the item tab, the project card and the cutlist pane). Task comments are not indexed in search.

### Review follow-up (2026-10-23): mutation locking

PATCH and status transitions lock the workspace-scoped task before reloading
visibility, ownership, status and versions. Validation and conflict messages use
the refreshed state after a lock wait. Normal task reads remain unlocked.
