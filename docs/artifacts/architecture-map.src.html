The request path

one rule, no exceptions

Every browser request enters through Next.js and leaves through a server-side proxy. The browser never calls FastAPI directly — it has no address for it. FastAPI is reachable only as api:8000 on the Docker network, and the session cookie is httpOnly, so a client-side fetch could not authenticate even if it found the host.

Browser fetch("/api/…") cookie: jf_session
redirects to /login on any non-public path

same-origin, server-side
Proxy Route Handler apps/web/app/api/[...proxy]/route.ts
internal Docker network only
API FastAPI api:8000 · 21 routers mounted in app/main.py
SQLAlchemy Core — text() queries, no ORM models
Data Postgres 16 Alembic 0001 → 0023

Auth is self-built: argon2id password hashes, an opaque 32-byte session token stored as its sha256, a sliding 14-day window with a hard 30-day cap. The layout at app/(app)/layout.tsx does a server-side fetchMe() and renders the chrome from the result, so the signed-in user is known before the first paint.

Workspace isolation is a query-level concern, not a middleware one. Every read and write gates on projects.workspace_id directly — the legacy pm_id chain was retired in migration 0014. Cross-workspace access returns 404, never 403: you are not told the row exists.

Who can do what

7 roles × 11 modules × 4 actions
Source apps/api/app/
auth/permissions.py

Enforced by require_permission(
  module, action)
in auth/rbac.py

Tap a role to isolate its column.

Six operational job roles map onto seven auth roles: CEO → admin, PM → manager, Drafter → drafter, Foreman and Machine team → editor, Procurement → purchase_officer, Estimator → estimator. The matrix is static and total — there is no per-record ACL anywhere in the system.

R read W write A approve C comment faint = not granted
The elevated drafter is the pattern to know. Drafter is the authoritative data-entry point, so it holds full read/write/approve/comment on seven modules — including approve, which editor never gets, even though editor outranks drafter on shop_floor. Drafter is deliberately held to read-and-comment on shop_floor and estimating: it enters the work, it does not run the floor or price it.

Two rules live in route handlers rather than the matrix, because they depend on who rather than what: a reviewer may not approve their own shop drawing or sample, and a worker may not override another worker's in-progress assignment.

SHT 04

The ten lifecycle stages

REQ → INST
Source items/queries.py
VALID_STAGE_KEYS

shop_floor/
lifecycle.py

Highlighted the five stages the shop floor actually schedules.

An item moves through ten milestones. Only the middle five happen on the shop floor and can carry a worker assignment; the rest are drafting, delivery and site work.

Stage order is enforced on completion, not on assignment. Marking CNC done before DOWN returns 409 STAGE_OUT_OF_ORDER with the missing stages listed. Two item flags reshape that order: paint_after_assembly moves PAINTED behind MADE, and painting_req = false drops PAINTED from the prerequisites entirely.

A completion can be undone. The worker who marked a stage done has five minutes to reverse it from their own kiosk banner; a supervisor can undo at any time. stage_completion_log is append-only — the undo writes an undone_at marker rather than deleting the row.
SHT 05

Six state machines

illegal transitions → 409 BAD_TRANSITION
Shape Each is a dict of legal targets checked under a row lock, then written in one transaction with its audit row.

Estimate revision

estimating/queries.py · _LEGAL_TRANSITIONS

draft → sent · withdrawn
sent → accepted · rejected · expired · withdrawn
accepted / rejected / expired / withdrawn — terminal

Only a draft accepts line edits. Only an accepted revision can convert to a project.

Shop drawing revision

shop_drawings/routes.py

draft → pending
pending → approved · rejected

The reviewer may not be the uploader. A partial unique index allows at most one in-flight revision per drawing; approval repoints current_revision_id atomically.

Sample

samples/routes.py

pending → approved · rejected

Rejection requires a review note, and reviewer ≠ creator. Rejected samples fall into the Archive subtab automatically; there are no revisions — you create a new sample.

Worker assignment

shop_floor/routes.py

assigned → in_progress · cancelled
in_progress → done · cancelled
done → in_progress (undo only)

A duplicate active assignment returns 409 carrying the existing assignment and worker, so the UI can offer reassign instead of asking the user to retry.

Cut schedule

cut_floor/routes.py

planned → running · cancelled
running → done · cancelled
done / cancelled — terminal

Delete is a soft cancel; cancelling twice is 409. Priorities are rewritten densely as 100, 200, 300 … when a day is reordered.

Procurement batch

procurement_v1/batches

status is derived in SQL, never persisted

Cancelling sets cancelled_at. A batch with live allocations returns 409 — remove the allocations first. Allocating beyond qty_received is also 409.

SHT 07

Invariants you must not "fix"

each one looks like a mistake and is not
Test If a change makes one of these simpler, the change is wrong. They encode differences the business actually has.
  1. 01

    Six material catalog tables stay six tables

    board_materials, hardware_materials, custom_made, benchtop_materials, appliances, equipment_hire share an abstract interface but have genuinely different lifecycles. Do not unify them. equipment_hire is the odd one: its primary key is hire_id, and inserting one requires a project_id.

  2. 02

    CutPlan and CutSchedule are two entities

    One is optimisation output, the other is the machine team's daily ordering. Deleting a plan that any live schedule references returns 409 PLAN_HAS_SCHEDULES.

  3. 03

    Batch → allocation → hardware line is one join

    That chain exists so "is this item blocked on a material?" is answerable in a single query, with no second window and no N+1. Keep it joinable.

  4. 04

    parts only has board_material_id

    There is no generic material FK, so a CV import of a non-board code stores NULL there. The resolution is not lost — it is preserved in the commit audit payload, the import run snapshot, and the part's comment as [material: table#id].

  5. 05

    Every mutation writes audit; item mutations write twice

    audit_log is workspace governance, item_edit_log is the item's own history, and both are written inside the same transaction as the change. The iSample approval ledger is not a table — it is audit_log filtered to sample.%.

  6. 06

    Archiving is soft; only CV mappings hard-delete

    Catalog rows, batches, samples and drawings all set an archived_at or cancelled_at. Re-archiving is 409 rather than a silent no-op, so the UI can tell the user nothing happened.

  7. 07

    Bulk catalog import is all-or-nothing

    Every row is validated before any row is inserted; one bad row returns {created: 0, errors: […]} and writes nothing. One audit row per import, not per row.

  8. 08

    No ORM models, no client state library

    The API is SQLAlchemy Core with text() queries throughout. The web app is raw fetch(), URL search params and controlled inputs — no TanStack Query, React Hook Form or Zustand. Match what is there.

SHT 08

Where things live

21 routers · 183 routes
Shape Every backend module is the same four files — schemas.py, queries.py, routes.py, __init__.py — mounted flat in main.py.

The web app mirrors this: one route folder per surface under apps/web/app/(app)/, with the six primary tabs and five secondary tabs declared in components/chrome/TabStrip.tsx. Design tokens live once, in app/globals.css, mirrored for JS in lib/tokens.ts. There is no tailwind.config.ts — Tailwind v4 is configured in CSS.

Two things are quarantined rather than live. legacy/ holds the original FileMaker-era prototypes — read-only reference, still the authority for the product surface via product_spec.md. And the old /procurement/* namespace (32 routes: orders, vendors, budget, approvals) is untouched by the v1 product surface, which uses procurement_v1 instead. Both are expected to converge later; neither is dead code you should delete.
