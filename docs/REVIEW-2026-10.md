## A. Bugs and data-safety (ranked)

- [x] **A1. Money typed `number` in `lib/pm-types.ts` — no change, the rule covers it (decided October 2026).** Line 553: `unit_cost: number | null`; `qty: number` at 244, 277, 554 and others. CLAUDE.md §6 says money and quantities arrive as strings and `number` "compiles then throws at `toFixed`". Evidence: `app/hardware_lines/schemas.py:22` declares `unit_cost: float | None`, so this field may be a float on the wire and therefore correct, which contradicts the rule. **Resolved:** `hardware_lines/schemas.py` still declares `unit_cost: float | None`, so it arrives as a JSON number and `number` is right. CLAUDE.md §6 already says a field the API declares `float` or `int` is typed `number` (it names `unit_cost`/`qty` in `lib/pm-types.ts`); only a Pydantic `Decimal` arrives as a string. Known limits, accepted: anyone who knows or guesses a slug can read those three totals, and a workspace with data is distinguishable from an unknown slug (an empty one is not); there is no rate limit; `projects_live` counts every project including closed ones (cosmetic); the login page hard-codes `hartwood-joinery`, so a second customer needs a different approach to this panel. `tests/test_public_stats.py` now pins it: only this workspace's rows, soft-deleted items' parts not counted, a supplier name counted once, unknown and missing slug.

## C. Performance (profiled)

**Method.** A scratch database with the seed plus one project of 1,000 items (each with a cutlist, area/room, 10 stage rows, 2 modules, 8 parts and hardware lines: about 10,000 stage rows and 8,000 parts) and one estimate of 300 lines (4 parts and 3 hardware each). Each endpoint was called in-process through the FastAPI test client (median of 5 runs after a warm-up), counting SQL statements with a SQLAlchemy cursor hook. This measures the API only: no network, no Next.js proxy, no browser rendering. A second project of 5,000 items checked how it scales. The scripts were scratch and are not committed.

| Endpoint | Wall | SQL statements (14 items → 1,000) | DB time | Payload |
| --- | ---: | :-: | ---: | ---: |
| Tracking list, 1,000 items | 137 ms | 9 → 9 | 34 ms | 1.5 MB |
| Tracking list, 5,000 items | 715 ms | — | — | 7.6 MB |
| Shop Floor board, 1,000 items | 55 ms | 5 → 5 | 37 ms | 189 KB |
| Shop Floor board, 5,000 items | 326 ms | — | — | 950 KB |
| Cutlists, 1,000 / 5,000 | 32 / 98 ms | 5 → 5 | 8 ms | 231 KB / 1.2 MB |
| Material summary, 1,000 / 5,000 | 23 / 49 ms | 6 | 8 ms | 59 / 297 KB |
| Estimate detail, 300 lines | 56 ms | 12 | 13 ms | 727 KB |
| Order preview, 300 lines | 66 ms | 14 | 16 ms | 230 KB |
| **Quote PDF, 300 lines** | **3,291 ms** | 19 | 24 ms | 100 KB |
| Item detail, item availability, home dashboard, QC dashboard, procurement queue, orders, projects, estimates list | 9-23 ms | 4-9 | ≤13 ms | ≤6 KB |

- [x] **C1. No N+1.** The statement count is identical for 14 and 1,000 items on every endpoint measured, so nothing queries per row. Database time is small everywhere (largest: 37 ms).
- [ ] **C1a. The Tracking list is a serialisation and payload cost, not a database cost.** For 1,000 items only 34 of 137 ms is SQL; the other ~100 ms is building and validating 1.5 MB of JSON, and it grows linearly (5,000 items: 715 ms, 7.6 MB). The API has no gzip middleware and I did not check whether the Next.js proxy compresses. Options if this ever matters: paginate or window the list, trim the per-row fields, or compress. Nothing to do at today's sizes.
- [ ] **C1b. The quote PDF takes 3.3 s for 300 lines.** The database is not the cause (24 ms); WeasyPrint rendering is. Fine for an on-demand download, but it blocks a worker for that time. Only worth acting on if quotes of this size are normal.
- [ ] **C1c. Shop Floor board** is the heaviest query: 34 of 37 ms DB time sits in one CTE (`item_pool`), and it grows linearly (326 ms at 5,000 items). Fine today.
- [x] **C3. Estimate payload.** 727 KB for 300 lines in one response (56 ms). Acceptable; a revision with thousands of lines would need paging.
- [ ] **C2. Web fetches.** 150 raw `fetch(` calls with no shared client. There is no caching or dedupe by design (§6). The cost is repeated boilerplate rather than speed. Not measured here (browser side).
